# US-101 Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Margin on the laptop and on the iPhone keep one set of data, syncing by themselves through the laptop whenever they can reach it.

**Architecture:** A pure `merge(local, shared, now)` in `src/domain/sync.ts` (beside US-99's `stamp`) applies the design's rules. A `useSync` hook in `src/state/useSync.ts` runs the cycle (read, validate, merge, write back against the revision, adopt locally) on a schedule, and reports a status that a `SyncStatus` line in Data shows. Data that arrives is committed with `adopt`, so it keeps the other device's dates.

**Tech Stack:** React 18, TypeScript, `fetch` to the same origin, Vitest, Playwright.

**Spec:** `docs/engineering/sync-design.md`, section 3. Depends on US-99 and US-100.

## Global Constraints

- Requests only to the app's own origin, `/api/sync`, with `X-Margin-Sync: 1`; nothing else after load.
- `lastBackupAt` never syncs: the merged result always keeps the local one.
- Test-first; AC IDs; Aditya runs git; full checks including both Playwright time zones; never touch 4180.

```markdown
# US-101, the laptop and the iPhone keep one set of data

US-101 As someone using Margin on my laptop and my phone,
I want what I add, change or delete on one to appear on the other by itself,
so that I never wonder which device has the real list.

Acceptance criteria:
AC-101.1 Margin syncs on opening, 3 s after the last change, every 60 s,
when the connection returns and when it comes back into view.
AC-101.2 For each record the newer change wins; a deletion beats an older
edit, and an edit after a deletion brings the record back.
AC-101.3 The newer lock wins, and every locked note comes from the side
whose lock won.
AC-101.4 A shared copy that does not validate is refused, and nothing
local changes.
AC-101.5 Data shows when it last synced, or why it could not, with
Sync now.
AC-101.6 Each device keeps its own last-backup date.
```

```ts
/**
 * US-101. One database from two: per record the newer change wins, a
 * deletion beats an older change, and locked notes follow the newer lock.
 * `local` wins ties, so merging a copy with itself changes nothing.
 */
export function merge(local: Database, shared: Database, now: Date): Database {
  // A clock more than a day ahead cannot win every conflict.
  const limit = shiftMinutes(now.toISOString(), 24 * 60);
  const when = (r: Keyed) =>
    r.changedAt > limit ? now.toISOString() : r.changedAt;
  // Equal times: the record whose JSON sorts later, the same on both devices.
  const newer = (a: Keyed, b: Keyed) =>
    when(a) !== when(b)
      ? when(a) > when(b)
      : JSON.stringify(a) > JSON.stringify(b);
  const marks = new Map<string, Deletion>();
  for (const mark of [...local.deleted, ...shared.deleted]) {
    const key = `${mark.kind}:${mark.id}`;
    const held = marks.get(key);
    if (!held || mark.at > held.at) marks.set(key, mark);
  }

  const lockSide =
    (shared.lock?.changedAt ?? '') > (local.lock?.changedAt ?? '')
      ? shared
      : local;
  const out = { ...local, lock: lockSide.lock } as Record<Collection, Keyed[]> &
    Database;

  for (const kind of COLLECTIONS) {
    const byKey = new Map<string, Keyed>();
    for (const record of local[kind] as Keyed[])
      byKey.set(keyOf(kind, record), record);
    for (const record of shared[kind] as Keyed[]) {
      const key = keyOf(kind, record);
      const held = byKey.get(key);
      if (!held || newer(record, held)) byKey.set(key, record);
    }
    let records = [...byKey.values()].filter((record) => {
      const mark = marks.get(`${kind}:${keyOf(kind, record)}`);
      if (mark && mark.at >= record.changedAt) return false;
      if (mark) marks.delete(`${kind}:${keyOf(kind, record)}`);
      return true;
    });
    if (kind === 'notes') {
      const sealedFrom = new Map(
        (lockSide.notes as Keyed[]).map((n) => [n.id, n as unknown as Note]),
      );
      records = records.map((n) => {
        const note = n as unknown as Note;
        const winner = sealedFrom.get(note.id);
        return note.sealed && winner?.sealed
          ? ({
              ...note,
              sealed: winner.sealed,
              body: winner.body,
            } as unknown as Keyed)
          : n;
      });
    }
    out[kind] = records;
  }

  out.deleted = [...marks.values()];
  out.lastBackupAt = local.lastBackupAt;
  return out;
}
```

Instants compare as strings because they are all `toISOString()` output, the one form `toInstant` and `stamp` write (US-94, US-99). Keep local's order for records it has, then new ones in shared's order, so lists do not shuffle.

```ts
const HEADERS = { 'X-Margin-Sync': '1' };

async function syncOnce(local: Database, adopt: (next: Database) => boolean) {
  for (let attempt = 0; attempt < 3; attempt += 1) {
    const got = (await (
      await fetch('/api/sync', { headers: HEADERS })
    ).json()) as {
      revision: number;
      db: unknown;
    };
    let shared: Database | null = null;
    if (got.db !== null) {
      const parsed = parseImport(JSON.stringify(got.db));
      if (!parsed.ok)
        throw new Error(`The shared copy is damaged: ${parsed.error}`);
      shared = parsed.db;
    }
    const merged = shared ? merge(local, shared, now()) : local;
    // Compared by key and time, not text: order alone is not a change.
    if (!shared || !sameRecords(merged, shared)) {
      const put = await fetch('/api/sync', {
        method: 'PUT',
        headers: { ...HEADERS, 'Content-Type': 'application/json' },
        body: JSON.stringify({ revision: got.revision, db: merged }),
      });
      if (put.status === 409) continue;
      if (!put.ok) throw new Error(`The laptop answered ${put.status}.`);
    }
    if (!sameRecords(merged, local)) adopt(merged);
    return;
  }
  throw new Error('Another device kept syncing at the same moment.');
}
```

The hook runs `syncOnce` on mount, `settle` ms after `db` changes, every 60 s, on `online` and on `visibilitychange` to visible; one at a time (skip if one is running). A `TypeError` from `fetch` means `unreachable`; any thrown `Error` means `failed` with its message. Hold `adopt` in a ref, as `useAutoBackup` does with `onBackedUp`.

Comparing with `lastBackupAt` normalised: build both strings from `{ ...db, lastBackupAt: null }` so a backup alone never triggers a write.

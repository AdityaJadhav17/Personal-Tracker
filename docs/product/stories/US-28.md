# US-28, things that come back

Approved and built 18 September 2026. The last feature Aditya named himself: "rent is 1st
of every month", "5pm PST". He re-enters that by hand twelve times a year, and
the same is true of anything weekly.

```
US-28  As someone whose rent is due every month,
       I want an item to come back after I finish it,
       so that I record it once instead of twelve times a year.

Priority: Should, built
Acceptance criteria:
  AC-28.1  Given an item set to repeat monthly,
           when I mark it done,
           then a new open item appears one month later with the same title,
           time, category, priority, course, goal and note.
  AC-28.2  Given an item set to repeat weekly,
           when I mark it done,
           then the new one is seven days later.
  AC-28.3  Given an item that does not repeat,
           when I mark it done,
           then nothing new appears, exactly as before.
  AC-28.4  Given I marked a repeating item done,
           when I press u to undo,
           then the finished one reopens and the one it created is removed.
  AC-28.5  Given a monthly item due on the 31st,
           when I mark it done in a month with fewer days,
           then the next one lands on the last day of that month rather than
           rolling into the one after.
  AC-28.6  Given a repeating item,
           when I look at it in the list,
           then it says that it repeats.
  AC-28.7  Given a version 1 or version 2 export,
           when I import it,
           then every item opens as not repeating and nothing is lost.
  AC-28.8  Given a repeating item,
           when I export and import the file,
           then it still repeats.
```

## Decisions

**One field on the item, not a template entity.** `repeat: 'none' | 'weekly' |
'monthly'`. A separate recurring-thing that spawns items would need its own
lifecycle, its own editing, and its own answer to "what happens when you change
it after three occurrences". The field is the smallest thing that solves rent.

**The next one is created when you finish the last one,** rather than a year of
them being generated up front. The dashboard answers "what do I do next" and
twelve rent rows would bury it, the calendar would fill with work nobody has
done, and every one of them would need deleting if you move out.

The cost is honest and worth stating: if you never mark rent done, the next one
never appears. A repeating item you ignore stops repeating, which is the same
failure as a repeating item you ignore in any calendar.

**Undo removes the one it created.** US-05 made `u` the inverse of marking done,
and it has to stay the inverse or finishing something by mistake leaves a
duplicate behind. The hook remembers the id it spawned alongside the id it
finished.

**A monthly item clamps rather than rolls.** The 31st of January plus one month
is not the 3rd of March. `toDueAt` already rejects impossible dates by reading
the fields back; the same trick gives the last day of a short month instead.

**Schema version 3, with a migration.** Both `load` and `parseImport` route
through `upgrade`, which is why a version 1 export still opens today. Adding
`repeat: 'none'` to every existing item follows the same path, and AC-28.7 is
the test that it worked.

## What it took

Schema version 3, `repeat` on the item, and `nextOccurrence` in `dates.ts`.
`markDone` became the only action that can add an item as well as change one.

**`upgrade` was rewritten as hops rather than branches.** It used to ask "is
this version 2?" and otherwise treat the input as version 1. Adding a third
version to that shape means every path through it has to be reconsidered. It
now applies one step at a time, so version 4 will be one more `if` rather than
a rethink.

**A careless find-and-replace broke `load` and the tests caught it.** Changing
every `version: 2` to `version: 3` also changed the guard that decided whether
the stored database already had its collections, so a current database fell
through the version 1 path and lost its goals, courses and reflections. The
comment above that branch warned about exactly this. The fix removed the branch
entirely: `load` now hands everything to `upgrade`, which is the only module
that should have an opinion about versions.

**Undo had to learn what "done" created.** US-05 made `u` the inverse of
marking done, and marking done can now produce a second item. The hook
remembers the pair, and AC-28.4 asserts the spawned one is removed rather than
left behind as a duplicate.

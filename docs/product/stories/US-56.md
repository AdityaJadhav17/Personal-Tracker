# US-56, deploys itself

Asked for 24 September 2026: "we have a ci pipeline i want a cd now I dont
want to be running npm deploy every time". Agreed: a push should reach the
app in four to eight minutes. Built the same day.

```
US-56  As the person who builds and uses this app,
       I want a push to main to reach the app once CI passes,
       so that I stop running npm run deploy by hand.

Priority: Should, built
Acceptance criteria:
  AC-56.1  A commit on main whose CI passed is deployed without anyone
           running a command, and shows on the next reload.
  AC-56.2  A commit whose CI failed is never deployed.
  AC-56.3  While CI is still running, the updater looks again every minute
           and deploys as soon as it passes, giving up after twenty minutes
           until its next run.
  AC-56.4  It deploys from its own clone, so the working folder, its branches
           and uncommitted edits never reach the app.
  AC-56.5  A deploy is recorded only once it checks out whole, so one that
           fails part way is redone on the next run.
  AC-56.6  With main already deployed, a run changes nothing.
```

## Decisions

**The laptop asks; nothing tells it.** A scheduled task runs
`scripts/update.mjs` every five minutes. It fetches `main` into
`%LOCALAPPDATA%\PersonalTracker-src`, asks GitHub's public API whether CI
passed for that commit, and if so builds into the deploy folder and runs the
same completeness check as `npm run deploy`. No token is stored, nothing
listens for a connection, and the app itself still makes no request.

**Not a self-hosted Actions runner.** It is the usual answer, and GitHub
advises against it on a public repository: a pull request from a fork would
run its workflow on this laptop. It would also mean a service holding a GitHub
token.

**Not a git hook.** A hook on commit deploys before CI has run, from whatever
branch is checked out, and never fires for changes merged on GitHub.

**Five minutes, then every minute while CI runs.** CI takes about three
minutes. A push lands four to eight minutes later, which is what Aditya asked
for; `Start-ScheduledTask 'Personal Tracker update'` right after a push makes
it about three. The public API allows sixty requests an hour, and a busy hour
uses about twenty.

**The marker lives in the deploy folder.** `deployed.txt` holds the commit.
The build empties the folder first, so a build that stops part way leaves no
marker, and the next run tries again rather than trusting a half-written
folder.

**No window.** The task runs Node through `conhost --headless`, so nothing
flashes up every five minutes.

**One log line per change.** `%LOCALAPPDATA%\PersonalTracker-update.log` gets
a line when something happens: a deploy, a failed CI, an error. The same
message twice in a row is written once, so an idle week adds nothing.

## What it took

**The partial deploys were looked for first.** Two manual deploys left an old
`index.html` beside new assets. Rebuilding into a folder while a preview
server served it and answered two hundred requests did not reproduce it, so
the server holding files open is not the cause. The cause is still unknown;
AC-56.5 is why it cannot stick.

Tested against scratch folders only: a fresh clone, an existing one, a
deploy folder missing its marker and its `index.html`, and a broken clone,
which logged one line and left the deployed app as it was. `verdict`, the
reading of CI's results, has unit tests beside the script.

A laptop task does not run on battery by default. The setup command allows
it.
